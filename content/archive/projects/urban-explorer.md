# Urban Explorer: the record, and the weekly job that was killed

Urban Explorer was a photo scavenger hunt web app that John built between December 2025 and April 2026, then stopped touching. Its one piece of unattended automation, a Cloud Function called `vibeRefreshAgent` that a Cloud Scheduler job fired every Monday, never did any work in its 30 weeks of life: it was deployed without the Google Maps key it needs, so every run logged one error line and quit. On 2026-10-15 that job and that function were deleted, after confirming that neither Roadtripper nor city-atlas-service refers to them. What Roadtripper does still lean on is the Firestore database `urbanexplorer` inside the same Google Cloud project, so the project and that database stay.

## 3. What the weekly function did, exactly

The weekly job was one Cloud Scheduler entry that sent an HTTP request every Monday to one second-generation Cloud Function, and that function quit on its first check every time because it had no Google Maps key. Everything below about the deployed resources is FACT from `gcloud scheduler jobs describe` and `gcloud functions describe` run on 2026-10-15 before deletion (output saved at `sources/2026-10-15-gcloud-inventory-before-delete.txt`).

The scheduler job: name `firebase-schedule-vibeRefreshAgent-us-central1`, location `us-central1`, schedule `0 3 * * 1` in time zone UTC (Coordinated Universal Time), which is Monday 03:00 UTC, Monday 12:00 JST (Japan Standard Time). Target: HTTP POST to `https://us-central1-urban-explorer-483600.cloudfunctions.net/vibeRefreshAgent` with an OIDC (OpenID Connect) token for the service account `971641856576-compute@developer.gserviceaccount.com`, attempt deadline 540 seconds. State ENABLED, created and last updated 2026-03-18T08:29:47Z, last attempt 2026-10-12T03:00:01Z, next scheduled 2026-10-19T03:00:00Z.

The function: name `vibeRefreshAgent`, environment GEN_2, region `us-central1`, runtime `nodejs20`, 512 MiB memory, 1 CPU, timeout 540 seconds, running as the same compute service account, created 2026-03-18T08:28:18Z and last updated 2026-03-18T08:29:29Z (never redeployed), labeled `deployment-tool: cli-firebase`. It ran as the Cloud Run service `viberefreshagent` at `https://viberefreshagent-971641856576.us-central1.run.app`, built from the source archive `vibeRefreshAgent/function-source.zip` (generation 1773822497959886, which is 2026-03-18T08:28:17Z) in the bucket `gcf-v2-sources-971641856576-us-central1`, with its container image in the Artifact Registry repository `gcf-artifacts`. Its environment variables were only `EVENTARC_CLOUD_EVENT_SOURCE`, `FIREBASE_CONFIG`, `FUNCTION_TARGET`, `GCLOUD_PROJECT` and `LOG_EXECUTION_ID`; it had no `secretEnvironmentVariables` block and no `GOOGLE_MAPS_KEY`.

The code: FACT from `functions/src/index.ts`: `onSchedule({ schedule: "0 3 * * 1", timeZone: "UTC", timeoutSeconds: 540, memory: "512MiB", region: "us-central1" }, ...)` reads `process.env.GOOGLE_MAPS_KEY`, and if it is empty logs `GOOGLE_MAPS_KEY not set. Aborting maintenance.` and returns. The options object declares no `secrets:` binding, which is how a Firebase function receives a Secret Manager value. Assessment: the key was never going to be present; the deploy configuration and the code agree on that, so the failure was built in from the first run, not caused by a later change.

What it would have done with a key, FACT from `functions/src/vibe-refresh-agent.ts`: `runWeeklyMaintenance` opens Firestore with `getFirestore()` and no database name (line 373; the compiled build at `functions/lib/vibe-refresh-agent.js:209` is the same call), which in the Firebase Admin SDK means the `(default)` database, not `urbanexplorer`. Step 1 reads every document in `cities` and keeps those whose `cache_metadata.last_refreshed` is older than seven days. Step 2, per stale city, queries `vibe_waypoints` where `city_id` matches and `is_active` is true, and calls `https://places.googleapis.com/v1/places/{place_id}?fields=businessStatus` for each waypoint, five at a time. Step 3 marks waypoints Google reports as CLOSED_PERMANENTLY with `is_active: false` in both `vibe_waypoints/{id}` and the nested `cities/{c}/neighborhoods/{n}/waypoints/{id}`, in batches of up to 498 writes. Step 4 updates the city's `cache_metadata` (last refreshed, next refresh, refresh count, a refresh log). Step 5 logs any neighborhood with two or more closures as needing regeneration, with a code comment that regeneration "is delegated to the build pipeline ... logged for manual follow-up or future automation", so nothing is regenerated. Steps 6 and 7 count `cities` and `pending_research` and write a `health_metrics/{YYYY-MM-DD}` document.

Two consequences follow. First, because it targets `(default)`, which has never held a `cities` collection (section 2), even a run with the key would have found zero stale cities, made zero Places calls and changed nothing in the real database (Assessment from the code and the counts). Second, the health-metrics step was never deployed: FACT, the source archive is timestamped 2026-03-18T08:28:17Z and the laptop's compiled `functions/lib/vibe-refresh-agent.js` (file date 2026-03-18) contains zero occurrences of `health_metrics` (`grep -c`), while commit `8abd05e` of 2026-03-24, which added that step, was never followed by a redeploy (function `updateTime` 2026-03-18T08:29:29Z). The admin page `src/app/admin/health/page.tsx:29-30` reads `health_metrics` from the `urbanexplorer` database through `adminDb`. Assessment: that page could never have shown a row, since the one writer of that collection was never deployed and, had it been, would have written to a different database.

The run history. FACT from `gcloud logging read` on `resource.type=cloud_run_revision AND resource.labels.service_name=viberefreshagent`: the four Mondays inside Cloud Logging's retention window, 2026-09-21, 09-28, 10-05 and 10-12, each show the same three lines within about two seconds of 03:00:01 UTC: an instance start ("Starting new instance. Reason: AUTOSCALING"), a successful startup probe, then `GOOGLE_MAPS_KEY not set. Aborting maintenance.` The matching Cloud Scheduler log entries for the same four dates are in the saved inventory file. FACT (Python date arithmetic): there were 30 Mondays from the first scheduled run on 2026-03-23 through the last on 2026-10-12. Assessment: all 30 runs ended the same way, because the deploy configuration never changed and the function was never redeployed; the earlier 26 runs are outside the log retention and cannot be shown individually.
