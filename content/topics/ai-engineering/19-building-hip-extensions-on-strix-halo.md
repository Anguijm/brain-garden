# Building HIP extensions against AMD's self-contained ROCm wheels

**Assessment.** AMD now ships PyTorch for unsupported consumer hardware as self-contained
wheels that bundle the ROCm runtime *and* the HIP compiler. That makes a GPU like the Radeon
8060S (gfx1151) usable without any system ROCm install. It does not, however, make building
third-party CUDA extensions work out of the box. Five distinct things are missing or wrong,
none of them in the extension's own code, and all five are fixable. This is the recipe,
recorded 2026-08-22 after getting [FlexGEMM](https://github.com/JeffreyXiang/FlexGEMM) to
build and run on a MINISFORUM MS-S1 MAX.

**FACT.** The measured end state on that machine: `sparse_submanifold_conv3d` runs on gfx1151
at a warm median of **0.12 ms** (7,254 active points, 32 to 32 channels, 3x3x3 kernel), against
**2,971 ms** on the first call. The first call is Triton autotuning and JIT, not the operation.
Anyone benchmarking one cold call will conclude the library is unusable by a factor of 25,000.

## The install that works

    pip install --index-url https://rocm.nightlies.amd.com/whl-multi-arch/ \
        "torch[device-gfx1151]" "torchvision[device-gfx1151]" torchaudio

One index for every GPU; the architecture is selected by the `[device-gfx1151]` extra rather
than by a per-architecture index URL. The wheels carry their own `hipcc`, and `ROCM_HOME`
resolves into `site-packages/_rocm_sdk_core`.

## The five things that break, in the order you hit them

**1. pip's build isolation installs a different PyTorch.** An extension's `setup.py` asks
torch whether it is a HIP build. Under build isolation it is asking a freshly downloaded CUDA
torch in a temporary directory, which says no, and the build then demands `CUDA_HOME`. Use
`--no-build-isolation` so it sees the ROCm torch that is actually installed.

**2. Python headers are absent.** `apt install python3.12-dev`. Ordinary, but it fails deep
inside a compiler invocation and reads like something worse.

**3. rocPRIM and rocThrust are not in any of the wheels.** Not in `rocm-sdk-core`, not in
`rocm-sdk-libraries`, not in `rocm-sdk-devel`. This matters more than it sounds, because
PyTorch's own `torch/headeronly/util/complex.h` includes `thrust/complex.h` unconditionally,
so *every* HIP extension built against these wheels hits it. Both libraries are header-only
and Apache-2.0; clone them and put them on `CPATH`.

**4. Those two libraries need CMake-generated version headers.** Cloning the source is not
enough: `rocthrust_version.hpp` and `rocprim_version.hpp` are generated by CMake from `.in`
templates. Generate them by hand, reading each version from its own `CMakeLists.txt` rather
than hardcoding a number. Note the two projects declare it differently, which will defeat a
single regex: rocThrust uses `rocm_setup_version(VERSION "4.0.0")`, rocPRIM uses
`set(VERSION_STRING "3.5.0")` on one line and passes the variable on the next.

**5. The runtime wheel omits the unversioned `.so` symlinks.** It ships `libamdhip64.so.7`
but not `libamdhip64.so`, and `ld -lamdhip64` resolves only against the latter, so the link
fails after every kernel has compiled successfully. Recreating the symlinks across the whole
`_rocm_sdk_core/lib` directory fixed 26 libraries at once. Sensible for a runtime-only
package; fatal the moment you build against it.

## Two traps that are not AMD's fault

**The header repos default to a dead branch.** rocPRIM, rocThrust and hipCUB all have
`develop_deprecated` as their default branch, last touched 2025-06-10. A plain `git clone`
of each gives you rocPRIM 3.5.0 against hipCUB 4.0.0, which fails with `no member named
'radix_key_codec' in 'rocprim::traits::get<T>'` - two AMD libraries disagreeing with each
other, which reads like a ROCm problem and is not. **Clone all of them at the same release
branch** (`-b release/rocm-rel-7.2` put all three at 4.2.0 and the mismatch vanished).

**The include layout differs between repos.** Some ship bare headers in `library/include`
(hipsparse.h); others already namespace them (`hipblas-common/hipblas-common.h`). Copying
both the same way buries the second one a directory too deep. Copy the tree, then flatten
any `X/X/` duplication.

**Generated headers are included from nested paths.** hipSOLVER includes its export header
as `internal/hipsolver-export.h`, so placing it only at the package root is not enough. They
are macro-only files; the cheap fix is to copy each into every subdirectory of its package.

**FACT.** The full shim for one build came to four cloned header libraries, seven more math
repos, 43 recreated `.so` symlinks across two lib directories, and 42 generated headers
scattered into subdirectories.

## What this says about the hardware

**Assessment.** Every failure above was packaging. None was code that would not run on the
GPU. The hipify pass over FlexGEMM's CUDA kernels reported **zero** unsupported CUDA function
calls, and all seven kernels then compiled for gfx1151 with `--offload-arch=gfx1151`. The
common belief that consumer AMD hardware cannot run this class of software is, at least here,
a statement about distribution rather than about silicon.

## The recipe has a short shelf life

**FACT.** On 2026-08-22 the same command, run twice about three hours apart against
`rocm.nightlies.amd.com`, produced `torch 2.13.0+rocm7.15.0a20260728` the first time and
`torch 2.14.0+rocm10.1.0a20260822` the second. That is a ROCm **major** version change
between two runs on the same day. The FlexGEMM build that had just succeeded against 7.15
then failed against 10.1 with a different error again: clang could not find the ROCm device
library, and ATen now demands a C++20 compiler.

**Assessment.** Two consequences worth planning around. A working install should be treated
as a pinned artifact and not casually recreated, because "reinstall it the same way" does not
give you the same thing. And any recipe of this kind, this one included, describes one night's
nightly rather than a stable platform. `pip freeze` the venv that works.

**Speculation.** The pattern is likely to hold for other CUDA extensions in the 3D-generation
ecosystem, since they mostly depend on the same small set of primitives. Worth testing before
assuming, and worth remembering that the AMD wheels are nightlies, so any of the five gaps
above may close or move without notice.

## What actually runs, and what does not (measured 2026-08-22)

Tested by building all of TRELLIS.2's native extension set for gfx1151 and running
[Pixal3D](https://huggingface.co/TencentARC/Pixal3D) end to end.

| extension | status |
|---|---|
| FlexGEMM (sparse conv) | **works**, 0.12 ms warm |
| NATTEN | **works** (pure PyTorch; the CUTLASS backend needs CUDA-only `libnatten`) |
| o_voxel | **builds and runs** |
| nvdiffrast | does not build: `Util.inl` is NVIDIA PTX inline assembly. Stubbed |
| CuMesh | **builds, fails at runtime** |

**FACT — the CuMesh defect, characterised.** `CuMesh::init` fails with
`hipErrorInvalidValue`, *and* leaves the HIP context unusable: a plain `tensor.max(0)`
afterwards raises the same error. Bracketing the pipeline with a trivial GPU op showed the
context healthy after `decode_shape_slat` and after `decode_tex_slat`, and broken
immediately after the CuMesh call. Catching the exception is therefore useless. The same
tensors (2,433,335 vertices, 5,096,820 faces, correct dtype, contiguous, indices in range)
initialise **fine** standalone, at sizes up to 16.7M vertices - so it is not the data, the
size, or an async error inherited from an earlier kernel.

**Assessment.** Pixal3D gets within one library of working: 2m40s of real inference
completes through sparse-structure, shape and texture generation plus NAF upsampling, and
fails only in mesh output. CuMesh is load-bearing there - it is used for hole filling *and*
for GLB extraction - so it cannot be routed around. The four documented ROCm source patches
(`::cuda::std::tuple`, the `Vec3f` host constructor, brace-init against explicit rocprim
constructors, NVCC-only flags) fix compilation but evidently not everything.

**Speculation, untested:** the header shim is built from `release/rocm-rel-7.2` while the
runtime is ROCm 7.15, so a struct or enum whose layout moved between those versions would
produce exactly this signature. Building the shim from a branch matching the runtime is the
next thing to try.
